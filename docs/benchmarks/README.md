# Saved CPU baselines

`cpu-baseline.json` and `cpu-baseline.csv` are generated by
`make cpu-baseline` from the fixed-seed synthetic `data/bench.log`.

* `mode=cpu-reference-single-thread` is the **semantic oracle**: one Python
  thread, full windowed pipeline, deterministic logical output.
* `mode=cpu-worker-threaded` is an **optional throughput probe only**. Input is
  split at LF boundaries and each block gets an independent history, so its
  alert counts are not compared to the oracle. The current CPython GIL makes
  this row slower; it is recorded to keep the format ready for a native worker.
* `native` summarizes the C ABI path (`libsentinel_cpu.so`), including the
  K2 `cells`, `mean` and `std` fields exposed in Sprint 4. Its separate K1/K2
  semantics are documented in `docs/algorithm-semantics.md` §7.
* `config_hash` is the API-compatible SHA-256 of the canonical detector config,
  so a baseline can be matched to jobs/chunk manifests.
* Timings are machine-specific; `input`, `detector`, `matches`, `features`,
  `alerts`, `cells`, `mean` and `std` are stable for a fixed input/config.

Regenerate with:

```bash
make dataset            # if data/bench.log is missing
make cpu-baseline
```

## CUDA memory pipeline (Sprint 5 / S5-D)

`cuda-memory-pipeline.json` is generated by
`PYTHONPATH=src python scripts/cuda_memory_pipeline.py` (or
`make cuda-memory-pipeline`). It records:

* a 2/4/8/16 MiB staging micro-batch sweep over the 95 MB synthetic log;
* a line-aligned 16 MiB-chunk stream over a generated 4.25 GiB file, i.e.
  larger than the 4096 MiB physical VRAM on the measured 16g laptop profile;
* `sentinel_timing` phase totals (allocation, H2D enqueue, kernel enqueue,
  D2H enqueue, native total) plus Python-side `wall_ms`;
* externally sampled `nvidia-smi` VRAM baseline/peak and the library's
  `peak_reported_device_bytes` estimate;
* bounded OOM retry count (currently zero).

The streamed file is regenerated locally under `data/` and is not committed.
`wall_ms` includes Python file reading, ctypes marshalling and line-flag
counting, so it is always larger than the sum of native `total_ms` values.
Phase numbers are diagnostics, not a device-only throughput or speedup claim;
the CPU/GPU kernel benchmark remains `make bench-kernels`.
